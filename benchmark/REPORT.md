## 4. 性能瓶颈分析

### 4.1 递归函数调用 (仍慢于 QuickJS)

**原因**:
- 每次 Call 仍要入栈 CallFrame 并 clone 函数值
- 指令解释器对算术/跳转路径未做专用快速路径
- 无内联缓存 / 无寄存器分配

**已做优化（Phase B）**:
- Value 堆类型改为 `Rc` / `Rc<RefCell>`，消除深拷贝
- 全局变量改为 `Vec` 槽表，Load/StoreGlobal 无 HashMap / String clone
- 数组/字典写操作原地修改
- 自递归尾调用复用栈帧（TCO）

**后续优化方向**:
- 调用帧复用 / 参数区重用（非尾调用场景）
- 算术与跳转 opcode 的内联快速路径
- 真寄存器 VM（Phase F）

## 4. 性能瓶颈分析

### 4.1 递归函数调用 (8.2x 慢于 QuickJS)

**原因**:
- QuickJS 使用引用计数，值传递开销小
- MaìLang 每次调用都克隆整个栈帧
- 递归深度 30 导致大量内存分配

**优化方向**:
- 实现尾递归优化 (TCO)
- 使用引用计数替代值克隆
- 优化调用帧管理

### 4.2 循环性能 (3.6x 慢于 QuickJS)

**原因**:
- 每次迭代的边界检查
- 指令解码开销

**优化方向**:
- 减少边界检查
- 使用计算跳转替代 match

## 6. 结论

| 场景 | vs QuickJS | vs Python | 评价 |
|------|------------|-----------|------|
| 字符串密集 | 1.0x | **9.9x 快** | ⭐ 优秀 |
| 循环密集 | 3.6x 慢 | **3.0x 快** | ⭐ 良好 |
| 函数调用 | 2.8x 慢 | **2.2x 快** | ⭐ 良好 |
| 深度递归 | 8.2x 慢 | 3.5x 慢 | ❌ 需优化 |

**下一步优化**:
1. 实现尾递归优化 (TCO)
2. 优化值传递（引用计数）
3. 减少循环边界检查
